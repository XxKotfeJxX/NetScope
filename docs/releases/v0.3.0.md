# NetScope v0.3.0 — Scheduled Monitoring

NetScope v0.3.0 turns one-off diagnostics into a lightweight monitoring
workspace. Named targets can now run on a schedule, retain availability and
latency history, suppress checks during maintenance, and notify operators when
a failure threshold is crossed or a target recovers.

## Highlights

- Save named targets with tags, selected probes, run options, and intervals.
- Run scheduled diagnostics without creating duplicate work across scheduler
  cycles.
- Track operational, warning, unavailable, paused, and maintenance states.
- Retain per-check latency, failure context, linked reports, and TLS expiry.
- Alert only on meaningful state transitions after the configured consecutive
  failure threshold.
- Deliver recovery and outage events to enabled webhook or email channels.
- Manage targets from a compact atlas, detailed timeline, and live operational
  journal.

## Run locally

Requirements:

- Docker with Compose support.
- Ports `5173` and `8080` available.
- A free PostgreSQL host port; set `POSTGRES_PORT` when `5432` is occupied.

```powershell
$env:POSTGRES_PORT = "5433"
docker compose --profile full up -d --build
```

Open <http://localhost:5173>, then choose **Targets** to save a target or
**Monitoring** to inspect the chronological journal.

Existing v0.2.0 PostgreSQL volumes are upgraded automatically by the embedded
migrations. Back up the database volume before upgrading a production-like
installation.

## Monitoring behavior

Each enabled target has an interval from 60 seconds to 24 hours and a failure
threshold from 1 to 20 checks. The scheduler claims due work atomically, skips
targets that already have a pending run, and records the resulting diagnostic
report. A target becomes unavailable only after its threshold is met. A later
successful or warning result records recovery and resets the failure counter.

Pause prevents future checks until resume. Active maintenance windows suppress
scheduled diagnostics and clearly mark the target until the window ends.

## Notifications

Webhook channels work without additional configuration. Payloads contain the
target, resulting status, transition message, and UTC observation time.
Redirects and URL credentials are rejected, delivery is time-bounded, and the
destination is resolved through NetScope's secure network-policy dialer.

To enable email channels, configure:

```dotenv
SMTP_HOST=smtp.example.com
SMTP_PORT=587
SMTP_USERNAME=netscope
SMTP_PASSWORD=replace-me
SMTP_FROM=NetScope <netscope@example.com>
SMTP_TLS_MODE=starttls
```

`SMTP_USERNAME` and `SMTP_PASSWORD` are optional but must be provided together.
Use `SMTP_TLS_MODE=tls` for implicit TLS or `none` only on a trusted local
network. Secrets belong in the deployment environment, never in the repository.

## Security model

Public deployments must set `NETWORK_POLICY=public`. This policy applies to
both diagnostic targets and webhook destinations and blocks private, loopback,
link-local, multicast, unspecified, and metadata addresses. NetScope v0.3.0
still has no application authentication; place it behind an access-control
layer and do not publish it directly.

## Known limitations

- Accounts, workspaces, roles, shared reports, comments, audit events, public
  links, and API keys arrive in v0.4.0.
- Production deployment guidance, integrated authentication, dark theme,
  onboarding, and the final accessibility pass are part of v1.0.0.
- Notification delivery is immediate and logs failures; durable retry queues
  are not included in this release.
