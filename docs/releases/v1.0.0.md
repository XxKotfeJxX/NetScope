# NetScope v1.0.0 — Public Release

NetScope v1.0.0 promotes the full diagnostics, monitoring, collaboration, and
public-report product line to a stable, production-documented release. The
release focuses on predictable operation: secure defaults, a versioned API,
accessible interaction, reproducible demo data, observability, and tested
recovery.

## Highlights

- Stable OpenAPI 3.1 contract under `/api/v1`, validated for syntax, internal
  references, unique operations, required routes, and response definitions.
- Hardened production Compose topology with Caddy automatic HTTPS, private
  API/PostgreSQL networking, dedicated diagnostic egress, health-gated startup,
  reduced Linux capabilities, a read-only API filesystem, and bounded
  container logs.
- Strict production browser-origin enforcement, Secure session cookies,
  security headers, and bounded rate limits for global, authentication,
  mutation, and public-report traffic.
- Aggregate Prometheus metrics plus structured 5xx and panic tracking with
  request-ID correlation and public-token path redaction.
- Warm Technical Atlas light theme and the new v1 dark palette, persisted per
  browser without changing the diagnostic information hierarchy.
- `Ctrl/Cmd+K` command palette for diagnostics, targets, history, schedules, and
  workspace switching.
- Compact mobile navigation, skip navigation, visible focus, keyboard command
  control, and reduced-motion behavior.
- First-run target presets and an idempotent public-API demo workspace seeder.
- Public `/docs` product and API manual available without an account.
- Verified custom-format PostgreSQL backup and staged restore tooling.

## Upgrade from v0.4.0

There are no new application schema migrations between v0.4.0 and v1.0.0, but
take and verify a database backup before replacing the application.

For the supported production deployment:

1. Check out the `v1.0.0` tag.
2. Copy `.env.production.example` to `.env.production`.
3. Set the public hostname, a long URL-safe database password, and the matching
   `DATABASE_URL`.
4. Confirm DNS points to the host and ports 80/443 are reachable.
5. Render the Compose configuration with `config --quiet`.
6. Build with `--pull`, start with `up -d`, and verify `/healthz`.

Production mode now refuses to start unless:

- `WEB_ORIGIN` is a path-free HTTPS origin;
- `SESSION_COOKIE_SECURE=true`;
- `CSRF_PROTECTION_ENABLED=true`.

The supplied production Compose file sets these values. Existing development
Compose behavior remains local and HTTP-based.

## Production security model

The public topology exposes only Caddy. Caddy terminates TLS, serves immutable
hashed assets, applies the web content security policy, hides `/readyz` and
`/metrics`, and forwards API requests over the private backend network.

The API:

- enforces the existing public-only SSRF policy for probes and webhooks;
- validates cookie-authenticated unsafe requests against the exact configured
  browser origin;
- ignores spoofable forwarding headers unless explicitly placed behind a
  trusted proxy;
- limits all API traffic and applies tighter authentication, mutation, and
  public-report limits;
- returns `RateLimit-*` and `Retry-After` metadata;
- emits generic client-facing 5xx errors and structured internal error context;
- stores aggregate metrics without user, workspace, target, or route labels.

## Backup and recovery

`scripts/backup-postgres.sh` creates a private PostgreSQL custom-format dump,
verifies its catalog, atomically publishes it, and writes a SHA-256 checksum.

`scripts/restore-postgres.sh` requires explicit confirmation, verifies the
checksum and dump, restores into a staging database while the API is online,
briefly stops the API for a database-name swap, restarts it, and waits for
readiness. The replaced database remains available under a timestamped name
until an operator completes post-restore verification.

Release-readiness CI executes this backup/restore path against an ephemeral
production-configured PostgreSQL service.

## Interface and accessibility

The existing Technical Atlas composition remains intentionally restrained:
technical lines, small radii, one accent, monospace only for measurements, and
no permanent sidebar.

v1.0 adds:

- the dark palette `#171A1C`, `#202427`, `#EEF0ED`, `#9EA4A8`, `#34393C`, and
  `#35A99A`;
- persisted theme selection with system preference as the first default;
- a compact navigation menu below 760 px;
- a skip link and clear focus indicators;
- full command-palette keyboard operation and focus return;
- reduced-motion handling;
- public docs and onboarding layouts that collapse to one column.

## Demo workspace

Set a unique `DEMO_PASSWORD` and run:

```sh
go run ./cmd/demo-seed
```

The command registers or signs in to the configured demo account and creates
three missing targets plus one initial run per target. Re-running it does not
duplicate the examples.

## API compatibility

The `/api/v1` prefix is the stable compatibility boundary for v1.x. Additive
fields and endpoints may arrive in minor releases. Removing or renaming
documented fields, changing their meaning, or changing required behavior
requires a new major API version.

API-key Bearer authentication remains workspace-scoped and capped at Operator.
Browser session cookies remain HttpOnly and SameSite. Public report links remain
read-only, expiring, revocable, hash-only at rest, and non-cacheable.

## Known limitations

- The supported production baseline is one application host.
- Rate-limit state is local to each API replica; multi-replica installations
  need a shared edge or distributed limiter.
- ICMP availability depends on host/container raw-socket capability.
- Metrics are disabled by default and require an additional private access path
  when enabled.
- SMTP delivery depends on the operator's provider and certificate policy.
