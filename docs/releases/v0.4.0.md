# NetScope v0.4.0 — Collaborative Workspaces

NetScope v0.4.0 turns the single-operator monitoring tool into an authenticated
workspace for teams. Diagnostic runs, saved targets, schedules, comments,
credentials, and audit records are isolated by workspace and governed by
explicit roles.

## Highlights

- Register an account with Argon2id password hashing and sign in through
  revocable opaque sessions stored as HttpOnly, SameSite cookies.
- Create and switch between isolated workspaces.
- Use Owner, Admin, Operator, and Viewer roles for least-privilege access.
- Add registered accounts to a workspace and manage their roles.
- Share saved targets, scheduled monitoring, run history, and reports with the
  workspace team.
- Add internal operational comments to diagnostic reports.
- Publish standalone read-only reports through expiring, revocable links.
- Issue workspace-scoped API keys with Viewer or Operator permissions.
- Review an immutable audit journal for membership, key, comment, and
  publication changes.

## Run locally

Requirements:

- Docker with Compose support.
- Ports `5173` and `8080` available.
- A free PostgreSQL host port; set `POSTGRES_PORT` when `5432` is occupied.

```powershell
$env:POSTGRES_PORT = "5433"
docker compose --profile full up -d --build
```

Open <http://localhost:5173> and register the first account. The first
registration creates an Owner workspace. Existing unassigned v0.3.0 runs and
targets are atomically claimed by this first workspace.

## Upgrade notes

The embedded migrations upgrade an existing v0.3.0 PostgreSQL volume
automatically. Back up the database before upgrading a production-like
installation.

For an upgrade containing legacy v0.3.0 data, register the intended
administrator before exposing the service to other users. The first successful
registration claims every legacy run and target that has no workspace.

New tables store users, sessions, workspaces, memberships, audit events, API
keys, report comments, and public report links. Existing diagnostics and
monitoring records gain a workspace reference.

## Roles

| Role     | Access                                                             |
| -------- | ------------------------------------------------------------------ |
| Owner    | Full workspace control and privileged role management             |
| Admin    | Manage Operator/Viewer members, API keys, comments, and links      |
| Operator | Create diagnostics and targets; comment on and publish reports     |
| Viewer   | Read workspace diagnostics, monitoring, comments, and link metadata |

Actors cannot change or remove their own membership. Repository transactions
also prevent the final Owner from being removed or demoted.

## Sessions and API keys

Passwords use Argon2id. Session and API-key plaintext values are never stored;
only SHA-256 token hashes are persisted. API keys:

- are fixed to exactly one workspace;
- can have only Viewer or Operator permissions;
- expire within at most 365 days;
- reveal their secret exactly once;
- stop authenticating immediately after revocation.

Provide a key as `Authorization: Bearer ns_key_...`. Browser sessions may use
the same header with an `ns_session_...` token or the session cookie.

## Public reports

An Operator can publish a completed or in-progress diagnostic report as a
standalone `/shared/:token` document. Public pages contain the diagnostic
record but no internal comments, member details, API keys, navigation, or
workspace controls.

Public-link tokens use 256 bits of random entropy and are stored only as
hashes. Invalid, expired, and revoked links all return `404`. Token path
segments are redacted from application access logs, and public responses use
`Cache-Control: no-store`.

## Security model

Workspace authorization applies at both transport and service boundaries.
Saved targets, nested monitoring resources, runs, comments, links, and API keys
are scoped by the active workspace. Cross-workspace resource access is denied.

Public deployments must set `NETWORK_POLICY=public`. This applies to probes and
webhook destinations and blocks private, loopback, link-local, multicast,
unspecified, and metadata addresses.

v0.4.0 is suitable for trusted self-hosted evaluation. Production hardening
such as strict CSRF/origin enforcement, deployment TLS guidance, backup and
restore procedures, error tracking, onboarding, and the final accessibility
pass is scheduled for v1.0.0.
